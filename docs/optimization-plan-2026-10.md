# 第一部分 · 用户本次实机反馈的三件事

## C1. 结算页「复习本单元」与「继续本单元词汇」玩家分不清　`[本次新提]`

### 位置

- `src/ui/screens/over.js:36-69`（两个按钮的文案与回调）
- `index.html:202-203`（`#oAgain` / `#oNext`）
- `src/app/runtime.js:1229` 附近（回调挂载）

### 现状（读代码得出的事实）

两个按钮的**真实语义完全相反**，但文案看不出区别：

| 按钮 | 出现条件 | 文案 | 实际行为 |
|---|---|---|---|
| `#oAgain` | 胜利且非自定义 | **复习本单元** | `onAgain()` —— **新开一轮**，本轮进度丢弃 |
| `#oNext` | 胜利、本单元还有词没完成 | **继续本单元词汇** | `onContinueUnit()` —— **同一轮**换一段地图继续，金币/道具/遗物全保留 |

代码里已经有注释写明这是有意设计：

> `over.js:44` — 「复习」永远是**新开一轮**去重练，不是「继续」。把两个语义混在一起会让玩家以为复习能顺带推进单元。

**问题在于：对玩家来说「复习本单元」和「继续本单元词汇」看起来是同一件事** —— 都是"接着练本单元的词"。而实际差别是**本轮进度是否保留**，这一点两个按钮的文案都没说。

### 证据

用户原话：「一关结束时，复习本单元和继续本单元有点搞不懂有什么区别」。

### 方案（三选一，**建议 A**）

**A. 文案改成说清后果（最小改动、零逻辑风险）**

| 按钮 | 现在 | 建议 |
|---|---|---|
| `#oAgain` | 复习本单元 | **重新开始本单元**（副标题：金币/道具/遗物清零，从头再来） |
| `#oNext` | 继续本单元词汇 | **继续练剩下 N 个词**（副标题：进度保留，不算新开一轮） |

把"复习"这个词从 `#oAgain` 上拿掉 —— 它同时暗示了"继续练"和"重来"，歧义的正是它。
自定义词表那一支（`G.unit === 0`）同理改成「重新开始自定义词表」。

**B. 合并成一个按钮 + 二次确认**

只有一个「继续本单元」，点 `#oAgain` 的语义走确认弹窗（"重新开始会清空本轮金币与道具，确定？"）。
收益：界面更简单。代价：多一次点击，且要新做弹窗组件。

**C. 保持文案，只加 `title` 提示**

最省事，但**手机上没有 hover** —— `title` 在触屏上等于不存在。
`equipment-panel.js` 的契约第 8 条已经写明"所有效果文案都必须是展开后直接可见的文本，不许只挂在 title 上"。**不推荐。**

### 验收

- 两个按钮的文案在**不看 title、不用 hover** 的前提下就能区分「进度保留」与「进度清空」
- `tests/unit/ui-modules.test.js` 的结算页 legacy 对照：文案属于**有意漂移**，要在对照里做归一化并单独断言新文案（参考该文件里 `stripArt` / `stripRound` 的既有写法）
- 新增 1 条断言：`#oAgain` 的文案不得含「复习」（防止回退）

### 风险

低。只动文案与 `title`，不动任何回调。**不要顺手改 `onAgain` / `onContinueUnit` 的行为** —— 那是两个不同的流程，混淆它们才是真正的 bug。

## C2. 关卡布局：营火过多、战斗数量不好　`[本次新提 · 已量化]`

### 位置

- `src/domain/map.js:4` `MAP_ROWS = 9`
- `src/domain/map.js:32-40`（节点类型权重）

### 现状（我实跑 20000 局模拟的结果）

```
一局地图总节点（均值）21.5

全图各类型占比 / 每局个数:
  battle   43.5%   每局 9.36
  event    15.2%   每局 3.27
  rest     20.2%   每局 4.34      ← 营火
  shop     10.2%   每局 2.20
  elite     6.2%   每局 1.33
  boss      4.7%   每局 1.00

开局第 0 行（3 个节点）的类型分布:
  battle   50.1%
  event    24.9%
  rest     25.0%      ← 每个开局节点有 1/4 概率是营火
  elite     0.0%

每局营火数: 最小 1  中位 4  最大 12  均值 4.34
营火 >= 4 的地图占比: 67.5%
营火 >= 5 的地图占比: 43.6%
```

**推算**：开局那一行 3 个节点各自 25% 是营火 ⇒ **约 15.6% 的地图开局就出现 2 个以上营火**。这与用户的观感一致。

> 注：下面「预期效果」那张表是**另一次独立的 20000 局采样**，所以现状列的均值是 4.36 而不是这里的 4.34
> —— 两者都是同一次无种子模拟的不同抽样，差异属正常噪声，不是两套数据打架。

权重来源（`map.js:34-40`）：

```js
// 前期（r <= 2）
roll < 0.52 ? 'battle' : roll < 0.68 ? 'event' : roll < 0.92 ? 'rest' : 'elite'
//    battle 52% / event 16% / rest 24% / elite 8%
// 后期
roll < 0.50 ? 'battle' : roll < 0.66 ? 'event' : roll < 0.80 ? 'rest' : roll < 0.92 ? 'shop' : 'elite'
//    battle 50% / event 16% / rest 14% / shop 12% / elite 8%
// 第 0 行
rnd(2) ? 'battle' : pick(['event', 'rest'])
//    battle 50% / event 25% / rest 25%
```

### 方案

**这一项是数值调整，必须有人拍板目标值。** 下面给一组建议起点，实现 agent 照做后**由用户实机定标**：

1. **开局行不给营火**：第 0 行改成 `rnd(2) ? 'battle' : 'event'`（battle 50% / event 50%）。
   理由：开局第一件事应该是打一场或遇一个事件；先给两次休息没有任何可恢复的东西。
2. **前期营火降到 ~12%**：`roll < 0.58 ? 'battle' : roll < 0.74 ? 'event' : roll < 0.86 ? 'rest' : 'elite'`
   （battle 58% / event 16% / rest 12% / elite 14%）。
3. **后期营火降到 ~10%、战斗提到 ~54%**：`roll < 0.54 ? 'battle' : roll < 0.68 ? 'event' : roll < 0.78 ? 'rest' : roll < 0.90 ? 'shop' : 'elite'`
   （battle 54% / event 14% / rest 10% / shop 12% / elite 10%）。

预期效果（**已用同样的 20000 局模拟实跑验证**，不是估算）：

| 指标 | 现状 | C2 方案 |
|---|---|---|
| 营火 均值 | 4.36 | **2.60** |
| 营火 中位 / 最大 | 4 / 13 | 2 / 9 |
| 营火 占比 | 20.3% | 12.1% |
| 战斗 每局 | 9.35 | **10.04** |
| 战斗 占比 | 43.5% | 46.7% |
| 第 0 行出现营火 | 25%/节点 ⇒ 约 15.6% 的地图开局 ≥2 个 | **0** |

⚠️ **`map.js` 的注释明确要求**：「随机调用次数与顺序必须完全一致，否则地图形状会与旧版漂移」。改权重时**不要改变 `random()` 的调用次数与顺序** —— 只改阈值比较的数字。

⚠️ 上面这组数值是**起点不是终点**。战斗密度提高 7% 会让整局更累，是否合适只能实机判断。**用户实机确认前不要定稿。**

### 验收

- `tests/unit/map.test.js`（或同目录）用**固定种子**跑出确定的地图，断言新分布
- 新增一条统计断言：20000 局里 `rest` 占比落在目标区间、第 0 行不出现 `rest`
- **e2e 已核查过，`baseline.spec.js` 不会因此变红**（我读了那条用例）：
  它只钉三件事 —— 前 3 行不含 `shop`、首领前一行含 `rest` 与 `shop`、`rows === 9`。
  这三样都不在本方案的改动范围内（首领前行是硬编码的 `['rest','shop',…]`，不动它）。
  `pause-resume.spec.js` 里出现的 `n.type = 'rest'` 是**测试自己赋值**，不依赖生成结果。

### 风险

- **中风险**：地图是 roguelite 的骨架，改了会整体改变节奏（战斗更密 = 更难更累）。
  **必须由用户实机验证后再定稿。**
- 若仍有 e2e 用例依赖固定地图形状而变红，那是**有意漂移**，按对照归一化的既有做法处理，**不许删断言**。

## C3. 商店磨砺石限购：卡面不刷新，买了 2 次还能点　`[本次新提 · 已实测复现]`

### 位置

- `src/app/encounters.js:54-64`（`buyWhetstone`）
- `src/app/encounters.js:350-352`（实时商店的卡片）
- `src/app/encounters.js:557-559`（暂停恢复路径的卡片）
- `src/data/balance.js`（`WHET_MAX_PER_RUN = 2`）

### 现状（我在真实浏览器里跑出来的）

```
进店:        whetBuys=0  maxhp=60  gold=1000
卡面: 生命上限 +10 并回满（本轮限 2 次，还剩 2 次）
买 1 次后:   whetBuys=1  maxhp=70  gold=930
卡面: 生命上限 +10 并回满（本轮限 2 次，还剩 2 次）   ← 没变
买 2 次后:   whetBuys=2  maxhp=80  gold=860
卡面: 生命上限 +10 并回满（本轮限 2 次，还剩 2 次）   ← 还是没变
买第 3 次后: whetBuys=2  maxhp=80  gold=860            ← 被正确拒绝了
```

**限购逻辑本身是对的**（第 3 次没扣钱、没加上限）。问题是**界面**：

1. **卡面的「还剩 N 次」永远停在 2**。因为商店只在**进入时**渲染一次，购买后只刷新了顶部的金币行（`refreshShopGold`，这正是上一批修的），**没有重画卡片**。
2. **买满之后卡片没有任何视觉区分** —— 不置灰、不禁用，玩家还会继续点，点了只得到一句 toast，卡片看起来仍可买。

用户原话：「商店里面加血量上限的东西总共只能买2次，限制可能有问题」—— 他看到的就是"显示还能买，但点了没用"。

### 方案

1. **购买后重画卡片**：`showShop()` 里那段点击处理器（`encounters.js:382-390`）在 `refreshShopGold()` 旁边再做一次「重画整屏商店」。
   ⚠️ **注意**：`showShop()` 每次会 `publish()` 一份新的 encounter 描述。重画必须保证**快照里那份与界面一致**，否则暂停恢复会对不上。建议把卡片渲染抽成 `renderShopCards(opts)`，点击后只重画 `#rPicks` 的 DOM，**不动 `current()`**（`opts` 里的 `fn` 是闭包，重画不能丢）。
2. **买满后置灰**：`buyWhetstone` 已经会返回拒绝文案，但卡片应在渲染时就反映状态 —— 给卡片加 `spent` 类（`equipment-panel.js` 的 `eq-spent` 是同一套语汇），CSS 里禁用点击或至少视觉降级。
3. **恢复路径同步**：`optionById` 那支（`:557`）也要用同一份渲染逻辑，否则"刷新一次卡片又变回可买"。

### 验收

- 买 1 次后卡面立刻变成「还剩 1 次」；买 2 次后变成「本轮已买满」且不可点
- 暂停 → 刷新 → 继续之后，卡面状态与刷新前**一致**
- 新增单测：连续买 3 次，断言 `maxhp` / `gold` / 卡面文案三者在第 3 次都不变
- 变异测试：去掉 `whetBuys` 守卫，上面这条必须变红

### 风险

低。但**"重画商店不能丢 `fn` 闭包"** 是个真实陷阱：`publish()` 出去的是脱敏后的描述（没有 `fn`），恢复路径靠 `optionById` 反查动作。重画时若误用 `current()` 的 options 重新绑回调，**所有购买按钮会失效**。

### VE-05 必须拍板的取舍（**不要跳过**）

`runtime.js:237-255` 的 `commit(force)` 注释写明：判据被刻意设计成「这个动作跑完了」而非「学习记录碰巧脏了」，**以换取"刷新绝不丢中途态"**。

所以 VE-05 的 5b（写前自检降频）**不能简单加 debounce** —— 必须先区分"状态事实"与"中途可丢态"，否则就是在拿一致性换性能。

**建议**：本轮只做 5a（`run.pool` 用 `bookId + unit` 引用替代，直接砍掉约一半快照体积），**5b 留到有人能明确写出取舍边界之后**。
⚠️ 5a 有个坑：自定义词表（unit 0）没有稳定来源，仍需落盘或用内容哈希寻址。

### VE-04 的验收必须能证伪

「只 patch 不重建」的正确性判据不是"看起来对"，而是：

```js
// 按键后，字母盘的节点对象引用必须不变
const before = [...document.getElementById('fBank').children];
// …按一个键…
const after = [...document.getElementById('fBank').children];
assert.ok(before.every((n, i) => n === after[i]));
```

外加：320px / 390px 布局与点击热区不变、**键盘焦点不丢**（这正是 `fight.js` 注释里说的"点一个字母点到一半按钮被换掉"）。

## 批次 3 · 数值正确性（VE-01 + 02 + 03 必须同生同死）

| ID | 一句话 |
