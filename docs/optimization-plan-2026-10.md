## C1. 结算页「复习本单元」与「继续本单元词汇」玩家分不清　`[本次新提]`

### 位置

- `src/ui/screens/over.js:36-69`（两个按钮的文案与回调）
- `index.html:202-203`（`#oAgain` / `#oNext`）
- `src/app/runtime.js:1229` 附近（回调挂载）

### 现状（读代码得出的事实）

两个按钮的**真实语义完全相反**，但文案看不出区别：

| 按钮 | 出现条件 | 文案 | 实际行为 |
|---|---|---|---|
| `#oAgain` | 胜利且非自定义 | **复习本单元** | `onAgain()` —— **新开一轮**，本轮进度丢弃 |
| `#oNext` | 胜利、本单元还有词没完成 | **继续本单元词汇** | `onContinueUnit()` —— **同一轮**换一段地图继续，金币/道具/遗物全保留 |

代码里已经有注释写明这是有意设计：

> `over.js:44` — 「复习」永远是**新开一轮**去重练，不是「继续」。把两个语义混在一起会让玩家以为复习能顺带推进单元。

**问题在于：对玩家来说「复习本单元」和「继续本单元词汇」看起来是同一件事** —— 都是"接着练本单元的词"。而实际差别是**本轮进度是否保留**，这一点两个按钮的文案都没说。

### 证据

用户原话：「一关结束时，复习本单元和继续本单元有点搞不懂有什么区别」。

### 方案（三选一，**建议 A**）

**A. 文案改成说清后果（最小改动、零逻辑风险）**

| 按钮 | 现在 | 建议 |
|---|---|---|
| `#oAgain` | 复习本单元 | **重新开始本单元**（副标题：金币/道具/遗物清零，从头再来） |
| `#oNext` | 继续本单元词汇 | **继续练剩下 N 个词**（副标题：进度保留，不算新开一轮） |

把"复习"这个词从 `#oAgain` 上拿掉 —— 它同时暗示了"继续练"和"重来"，歧义的正是它。
自定义词表那一支（`G.unit === 0`）同理改成「重新开始自定义词表」。

**B. 合并成一个按钮 + 二次确认**

只有一个「继续本单元」，点 `#oAgain` 的语义走确认弹窗（"重新开始会清空本轮金币与道具，确定？"）。
收益：界面更简单。代价：多一次点击，且要新做弹窗组件。

**C. 保持文案，只加 `title` 提示**

最省事，但**手机上没有 hover** —— `title` 在触屏上等于不存在。
`equipment-panel.js` 的契约第 8 条已经写明"所有效果文案都必须是展开后直接可见的文本，不许只挂在 title 上"。**不推荐。**

### 验收

- 两个按钮的文案在**不看 title、不用 hover** 的前提下就能区分「进度保留」与「进度清空」
- `tests/unit/ui-modules.test.js` 的结算页 legacy 对照：文案属于**有意漂移**，要在对照里做归一化并单独断言新文案（参考该文件里 `stripArt` / `stripRound` 的既有写法）
- 新增 1 条断言：`#oAgain` 的文案不得含「复习」（防止回退）

### 风险

低。只动文案与 `title`，不动任何回调。**不要顺手改 `onAgain` / `onContinueUnit` 的行为** —— 那是两个不同的流程，混淆它们才是真正的 bug。

## C2. 关卡布局：营火过多、战斗数量不好　`[本次新提 · 已量化]`

### 位置

- `src/domain/map.js:4` `MAP_ROWS = 9`
- `src/domain/map.js:32-40`（节点类型权重）

### 现状（我实跑 20000 局模拟的结果）

```
一局地图总节点（均值）21.5

全图各类型占比 / 每局个数:
  battle   43.5%   每局 9.36
  event    15.2%   每局 3.27
  rest     20.2%   每局 4.34      ← 营火
  shop     10.2%   每局 2.20
  elite     6.2%   每局 1.33
  boss      4.7%   每局 1.00

开局第 0 行（3 个节点）的类型分布:
  battle   50.1%
  event    24.9%
  rest     25.0%      ← 每个开局节点有 1/4 概率是营火
  elite     0.0%

每局营火数: 最小 1  中位 4  最大 12  均值 4.34
营火 >= 4 的地图占比: 67.5%
营火 >= 5 的地图占比: 43.6%
```

**推算**：开局那一行 3 个节点各自 25% 是营火 ⇒ **约 15.6% 的地图开局就出现 2 个以上营火**。这与用户的观感一致。

> 注：下面「预期效果」那张表是**另一次独立的 20000 局采样**，所以现状列的均值是 4.36 而不是这里的 4.34
> —— 两者都是同一次无种子模拟的不同抽样，差异属正常噪声，不是两套数据打架。

权重来源（`map.js:34-40`）：

```js
// 前期（r <= 2）
roll < 0.52 ? 'battle' : roll < 0.68 ? 'event' : roll < 0.92 ? 'rest' : 'elite'
//    battle 52% / event 16% / rest 24% / elite 8%
// 后期
roll < 0.50 ? 'battle' : roll < 0.66 ? 'event' : roll < 0.80 ? 'rest' : roll < 0.92 ? 'shop' : 'elite'
//    battle 50% / event 16% / rest 14% / shop 12% / elite 8%
// 第 0 行
rnd(2) ? 'battle' : pick(['event', 'rest'])
//    battle 50% / event 25% / rest 25%
```

### 方案

**这一项是数值调整，必须有人拍板目标值。** 下面给一组建议起点，实现 agent 照做后**由用户实机定标**：

1. **开局行不给营火**：第 0 行改成 `rnd(2) ? 'battle' : 'event'`（battle 50% / event 50%）。
   理由：开局第一件事应该是打一场或遇一个事件；先给两次休息没有任何可恢复的东西。
2. **前期营火降到 ~12%**：`roll < 0.58 ? 'battle' : roll < 0.74 ? 'event' : roll < 0.86 ? 'rest' : 'elite'`
   （battle 58% / event 16% / rest 12% / elite 14%）。
3. **后期营火降到 ~10%、战斗提到 ~54%**：`roll < 0.54 ? 'battle' : roll < 0.68 ? 'event' : roll < 0.78 ? 'rest' : roll < 0.90 ? 'shop' : 'elite'`
   （battle 54% / event 14% / rest 10% / shop 12% / elite 10%）。

预期效果（**已用同样的 20000 局模拟实跑验证**，不是估算）：

| 指标 | 现状 | C2 方案 |
|---|---|---|
| 营火 均值 | 4.36 | **2.60** |
| 营火 中位 / 最大 | 4 / 13 | 2 / 9 |
| 营火 占比 | 20.3% | 12.1% |
| 战斗 每局 | 9.35 | **10.04** |
| 战斗 占比 | 43.5% | 46.7% |
| 第 0 行出现营火 | 25%/节点 ⇒ 约 15.6% 的地图开局 ≥2 个 | **0** |

⚠️ **`map.js` 的注释明确要求**：「随机调用次数与顺序必须完全一致，否则地图形状会与旧版漂移」。改权重时**不要改变 `random()` 的调用次数与顺序** —— 只改阈值比较的数字。

⚠️ 上面这组数值是**起点不是终点**。战斗密度提高 7% 会让整局更累，是否合适只能实机判断。**用户实机确认前不要定稿。**

### 验收

- `tests/unit/map.test.js`（或同目录）用**固定种子**跑出确定的地图，断言新分布
- 新增一条统计断言：20000 局里 `rest` 占比落在目标区间、第 0 行不出现 `rest`
- **e2e 已核查过，`baseline.spec.js` 不会因此变红**（我读了那条用例）：
  它只钉三件事 —— 前 3 行不含 `shop`、首领前一行含 `rest` 与 `shop`、`rows === 9`。
  这三样都不在本方案的改动范围内（首领前行是硬编码的 `['rest','shop',…]`，不动它）。
  `pause-resume.spec.js` 里出现的 `n.type = 'rest'` 是**测试自己赋值**，不依赖生成结果。

### 风险

- **中风险**：地图是 roguelite 的骨架，改了会整体改变节奏（战斗更密 = 更难更累）。
  **必须由用户实机验证后再定稿。**
- 若仍有 e2e 用例依赖固定地图形状而变红，那是**有意漂移**，按对照归一化的既有做法处理，**不许删断言**。

## C3. 商店磨砺石限购：卡面不刷新，买了 2 次还能点　`[本次新提 · 已实测复现]`

### 位置

- `src/app/encounters.js:54-64`（`buyWhetstone`）
- `src/app/encounters.js:350-352`（实时商店的卡片）
- `src/app/encounters.js:557-559`（暂停恢复路径的卡片）
- `src/data/balance.js`（`WHET_MAX_PER_RUN = 2`）

### 现状（我在真实浏览器里跑出来的）

```
进店:        whetBuys=0  maxhp=60  gold=1000
卡面: 生命上限 +10 并回满（本轮限 2 次，还剩 2 次）
买 1 次后:   whetBuys=1  maxhp=70  gold=930
卡面: 生命上限 +10 并回满（本轮限 2 次，还剩 2 次）   ← 没变
买 2 次后:   whetBuys=2  maxhp=80  gold=860
卡面: 生命上限 +10 并回满（本轮限 2 次，还剩 2 次）   ← 还是没变
买第 3 次后: whetBuys=2  maxhp=80  gold=860            ← 被正确拒绝了
```

**限购逻辑本身是对的**（第 3 次没扣钱、没加上限）。问题是**界面**：

1. **卡面的「还剩 N 次」永远停在 2**。因为商店只在**进入时**渲染一次，购买后只刷新了顶部的金币行（`refreshShopGold`，这正是上一批修的），**没有重画卡片**。
2. **买满之后卡片没有任何视觉区分** —— 不置灰、不禁用，玩家还会继续点，点了只得到一句 toast，卡片看起来仍可买。

用户原话：「商店里面加血量上限的东西总共只能买2次，限制可能有问题」—— 他看到的就是"显示还能买，但点了没用"。

### 方案

1. **购买后重画卡片**：`showShop()` 里那段点击处理器（`encounters.js:382-390`）在 `refreshShopGold()` 旁边再做一次「重画整屏商店」。
   ⚠️ **注意**：`showShop()` 每次会 `publish()` 一份新的 encounter 描述。重画必须保证**快照里那份与界面一致**，否则暂停恢复会对不上。建议把卡片渲染抽成 `renderShopCards(opts)`，点击后只重画 `#rPicks` 的 DOM，**不动 `current()`**（`opts` 里的 `fn` 是闭包，重画不能丢）。
2. **买满后置灰**：`buyWhetstone` 已经会返回拒绝文案，但卡片应在渲染时就反映状态 —— 给卡片加 `spent` 类（`equipment-panel.js` 的 `eq-spent` 是同一套语汇），CSS 里禁用点击或至少视觉降级。
3. **恢复路径同步**：`optionById` 那支（`:557`）也要用同一份渲染逻辑，否则"刷新一次卡片又变回可买"。

### 验收

- 买 1 次后卡面立刻变成「还剩 1 次」；买 2 次后变成「本轮已买满」且不可点
- 暂停 → 刷新 → 继续之后，卡面状态与刷新前**一致**
- 新增单测：连续买 3 次，断言 `maxhp` / `gold` / 卡面文案三者在第 3 次都不变
- 变异测试：去掉 `whetBuys` 守卫，上面这条必须变红

### 风险

低。但**"重画商店不能丢 `fn` 闭包"** 是个真实陷阱：`publish()` 出去的是脱敏后的描述（没有 `fn`），恢复路径靠 `optionById` 反查动作。重画时若误用 `current()` 的 options 重新绑回调，**所有购买按钮会失效**。

## C4. 跳过 / 逃跑的代价改成「百分比 + 地板」　`[本次新提 · 与既有设计论证冲突 · 先拍板再动手]`

### 位置

| 文件 | 位置 | 内容 |
|---|---|---|
| `src/data/balance.js` | `:8` | `export const SKIP_HP_COST = 50;` |
| `src/app/combat.js` | `:575-604` | `skipFight()` |
| `src/app/combat.js` | `:607-615` | `fleeFight()` |
| `src/ui/screens/fight.js` | `:236-245` | 两个按钮的文案与禁用逻辑（**动态计算的**） |
| `index.html` | `:153-154` | 按钮初始文案（会被 JS 覆盖，但要同步改，否则首帧闪一下旧文案） |

### 现状

```js
// 跳过（combat.js:575-604）
if (G && hasR('ghost') && !G.ghostUsed) { … 免费撤退，影分身 … return true }   // 额度分支
B.myHp -= SKIP_HP_COST;                                                          // 固定 50 点
if (B.myHp <= 0) { B.myHp = 0; toast('跳过：生命耗尽…'); loseFight(); return true }  // 付不起 = 战败
B.over = true; finishNode();

// 逃跑（combat.js:607-615）
if (!B || B.over || !G || G.gold < 10) return false;   // 金币 < 10 → 整个动作拒绝
G.gold -= 10;                                          // 固定 10 金币
B.over = true; toast('逃跑成功，损失 10 金币'); finishNode();
```

| | 现在的代价 | 不足时 |
|---|---|---|
| 跳过 | 固定 **50 点生命** | 生命 ≤ 50 → 归零 + `loseFight()` 战败（**不许用 `Math.max(1,…)` 保命**）|
| 逃跑 | 固定 **10 金币** | 金币 < 10 → `fleeFight` 返回 false，按钮也 `disabled`（`fight.js:244`）|

### ⚠️ 这条推翻了 `balance.js` 里一段明确的设计论证

```js
// SKIP_HP_COST = … 固定点数而不是百分比：
// 百分比在低血时会退化成「扣一点点还能苟住」，玩家可以无限白嫖撤退，
// 于是「跳过」比认真打完更划算。固定 50 让低血撤退成为一次真实决策。
```

**「最低 50」的地板正好补上这个漏洞** —— 低血时仍然至少付 50，不会退化成白嫖。
所以这条论证**不构成反对**，可以放心改。但它也说明：**地板是这套设计的支点，不能省**。

### 规格（用户原话）

- 逃跑 → 扣 **50% 的钱**，最低 50 金钱
- 跳过 → 扣 **50% 的生命**，最低 50 生命

### 🚨 先说一个反直觉的实测结论：**跳过这条按字面实现，几乎不改变任何东西**

玩家的生命上限构成：基础 `70` + 角色（最高战士 `+15`）+ 知识成长（封顶 `+12`）+ 磨砺石（`2×10`）
⇒ **可达最高上限 117**。而 `B.myHp` 是**当前**生命，只会更低。

于是 `max(50, floor(当前生命 × 50%))`：

| 当前生命 | 新代价 | 现在 | 变化 |
|---|---|---|---|
| 40 | 50 | 50 | 无 |
| 82（典型满血） | 50 | 50 | **无** |
| 100 | 50 | 50 | **无** |
| 117（极限满血） | 58 | 50 | +8 |

**除了极限构筑，代价一点没变。** 如果意图是"跳过要更痛"，这条规格**达不到目的**。
真正的杠杆是**地板**，不是百分比。三个选项，需要拍板：

| 方案 | 典型满血(82)的代价 | 说明 |
|---|---|---|
| (a) 50% 当前生命，地板 50 | 50（不变） | **用户原话，但几乎无效** |
| (b) 50% 当前生命，地板 70 | 70 | 地板提到与"一次普通失误"同量级，能感到痛 |
| (c) 50% 生命**上限**，地板 50 | 41 → 50（不变） | 换成上限也救不了 —— 典型上限 82 的一半仍是 41 |

**推荐 (b)**：把地板提高到 60–70 区间。数值请用户实机定标。

### 逃跑那条反而是大改

## C5. 遗物的「描述」与「实现」对不上（3 件）　`[本次新发现 · 已逐条核实]`

### 为什么值得修

这是一个**照着描述做构筑决策**的 roguelite。描述没写的效果 = 玩家评估不了这件遗物；
描述**夸大**的效果 = 玩家按错误预期选它。两类都会让构筑决策失真。

### 逐条证据（全部在归档旧版里就有，**不是最近几批引入的**）

#### ① 永动电池 —— 有一个描述没写的效果

```js
// src/data/relics.js:25
{id:'battery', n:'永动电池', d:'每通过一层回复 8 点生命', …}

// src/app/runtime.js:524  —— 描述说的那个，正确
if(has(G.relics,'battery')) G.hp=Math.min(G.maxhp,G.hp+8);
// src/domain/run.js:159 同理
if (run.relics.indexOf('battery') >= 0) run.hp = Math.min(run.maxhp, run.hp + 8);

// src/app/combat.js:445  —— 这个描述里没有
if (hasR('battery') && B.wordsDone % 3 === 0) { B.myHp = Math.min(G.maxhp, B.myHp + 3); toast('🔋 永动电池：回复 3 生命'); }
```
旧版 `tests/fixtures/legacy.html:4069` 有一模一样的行 ⇒ **历史遗留**。
（自增顺序正确：`combat.js:435` 先 `wordsDone++`，`:445` 再判 `% 3`，没有 0 号词的 off-by-one。）

#### ② 学者之书 —— 描述**夸大**，另有第三个效果没写

```js
// src/data/relics.js:27
{id:'scholar', n:'学者之书', d:'战斗胜利额外获得 1 张「先知卡」', …}
```
`d` 读起来像「每场胜利都给一张」。实际：

```js
// src/app/encounters.js:428  —— 1/3 概率才给
if (hasR('scholar') && (activeSynergies(G.relics).some(s => s.id === 'alchemist') || rnd(3) === 0)) { … 先知卡 … }
// src/app/runtime.js:836  —— 描述里完全没提的第二个效果
if(hasR('scholar') && B.wordsDone===1){ B.hintUsed=1; B.hintTotal=1 }   // 第一个词完成后揭示首字母
```
旧版 `legacy.html:4311` 也是 `rnd(3)===0` ⇒ 概率是原设计，**描述一直写错了**。

#### ③ 专注头环 —— 有一个描述没写的效果

```js
// src/data/relics.js —— d:'连击中断不清零，改为保留一半'
// src/app/combat.js:486  —— 描述说的那个，正确
B.combo = hasR('focus') ? Math.floor(B.combo / 2) : 0;
// src/app/combat.js:425  —— 这个描述里没有
if (hasR('focus') && B.combo > 0 && B.combo % 6 === 0) B.dmgBonus += 5;
```
⚠️ 已确认这一行**不是**「连击共鸣」组合技 —— 那个走 `relic-rules.js` 的 `synergyBonuses`，
是另一条独立实现。所以它是专注头环**单件**的隐藏效果。

### 我核对过、**没有**问题的部分（供参考，省得重复查）

- **道具** 8 件的描述与实现一致（`reveal` 的「消耗 1 次提示额度」是上一批刚修正的）
- **角色** 6 件的 `mod` 字段全部接线正确（`hint/noise/combo/gold/regen/leech/hp` 在 `run.js` 各有一处应用）
- **聚宝盆** 的 +25 确实生效（`runtime.js:1059` `g += victoryGoldBonus(G.relics)`）
- 提示水晶 +2、护盾符文 15、荆棘 5、锻造台 20/12、贪婪之眼 ×1.5、幸运草首次免伤 —— 都对得上

### 方案（**需要拍板，不是纯技术活**）

每一件都要二选一，**不能默默改描述糊过去**：

| 遗物 | 选项 A：改描述（承认既有效果） | 选项 B：删除隐藏效果 |
|---|---|---|
| 永动电池 +3/3词 | `d` 补上「并每完成 3 个词回复 3 点生命」 | 删 `combat.js:445` |
| 学者之书 首字母 | `d` 补上「第一个词完成后揭示下一词首字母」 | 删 `runtime.js:836` |
| 学者之书 先知卡 1/3 | `d` 改成「战斗胜利时**有机会**获得 1 张先知卡」 | 改成必定获得 |
| 专注头环 +5/6连击 | `d` 补上「每 6 连击额外 +5 增伤」 | 删 `combat.js:425` |

**建议全部走 A（改描述）**：这三件遗物在旧版就存在这些效果，
删掉会改动已上线的平衡；而补描述是**零行为变化**的纯文案修复，风险最低。

### 验收

- 每件遗物的 `d` 与代码效果**逐条对得上**
- 新增一条测试：断言「描述里提到的每个数字，都能在代码里找到」——
  这条不好写通用版，**退而求其次**：为上面 4 处各写一条具名断言
- ⚠️ 描述文案会出现在多个界面（事件卡、商店卡、装备面板、图鉴），
  改 `data/relics.js` 一处即可，但**要跑一遍 e2e 确认没有哪个界面把文案写死了**
- `tests/unit/relic-*.test.js` 里若有断言旧描述的，属于**有意漂移**，需按对照归一化的既有做法处理

### 风险

低。纯文案 + 可能的删码。但**如果选 B（删效果）就变成数值改动**，必须由用户实机确认。
